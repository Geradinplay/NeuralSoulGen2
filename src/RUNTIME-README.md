# NeuralSoul — рабочее ядро и патч для src

## Установка

Остановите приложение. Содержимое `neuralsoul-backend-src-patch.zip` распакуйте прямо в существующую папку **src**, с заменой файлов. В архиве `main/java/...`, `test/java/...` и эта инструкция. Вложенной папки `src` нет. Старые файлы не нужно удалять.

Патч предназначен для Maven-проекта NeuralSoul из этого диалога и включает исправления размеров окон и размещения ввода только во вкладке «Чат». Новых Maven-зависимостей нет; `pom.xml` менять не требуется. Java 17+.

Из корня проекта, где находится `pom.xml`:

```sh
mvn clean javafx:run
```

## Первый запуск

1. Запустите свой LLM-сервер, например llama.cpp. Java-приложение не содержит моделей и не запускает EXE/Python-процессы серверов.
2. Адреса сервисов и параметры API задаются в конфигах `llm.properties`, `stt.properties` и `tts.properties` (каталог `~/.neuralsoul/config`); GUI-редактор вкладки «Сервисы и API» удалён, вкладка переименована в **Схему** и показывает только граф архитектуры моделей.
3. Укажите **Base URL**, **API path** и при необходимости Model ID. Base URL — корень сервера, обычно без `/v1`.
4. Нажмите «Сохранить» или «Подключить» под нужным сервисом; «Подключить» сначала сохраняет форму.
5. Во вкладке **Модели** нажмите **Обновить с сервера** и выберите модель. Также можно ввести Model ID вручную в чате. Пустой ID использует `llm.properties:model`, а если он пустой — не отправляет поле model; сервер должен поддерживать это.
6. В **Чате** отправьте сообщение. Ответ поступает от HTTP API, DemoBackend больше не используется приложением.
7. Для озвучивания включите переключатель «Голос» и настройте TTS. Микрофон — отдельная кнопка: первый клик начинает запись, второй распознаёт и отправляет её. Во вкладке **Голос** есть загрузка WAV и отдельный тест TTS.
8. **Стоп** прерывает текущую операцию/воспроизведение/запись. **Новый чат** дополнительно очищает историю, передаваемую LLM.

Автоподключение по умолчанию включено. Если оно отключено в настройках пайплайна, сначала нажмите «Подключить» для нужных сервисов. Время записи ограничено (по умолчанию 60 секунд); после достижения лимита нажмите микрофон повторно, чтобы отправить накопленную запись.

## Конфиги и локаторы

`ConfigLocator` создаётся один раз в `NeuralSoulApp`, передаётся зависимым объектам и предоставляет типизированные загрузчики через `ConfigLoader<T>`.

| Загрузчик | Файл | Что хранит |
|---|---|---|
| `LlmConfigLoader` | `llm.properties` | URL, маршруты API/health, имя env-переменной ключа, timeout, model, system prompt, temperature, max tokens |
| `SttConfigLoader` | `stt.properties` | URL, маршрут распознавания, model, language, имя multipart-поля WAV |
| `TtsConfigLoader` | `tts.properties` | URL, протокол OPENAI/COQUI, model, voice/speaker, language, speed |
| `PipelineConfigLoader` | `pipeline.properties` | число пар истории, лимит символов контекста, длительность микрофона, автоподключение |
| `GuiConfigLoader` | `gui.properties` | настройки CPU/GPU, RAM/VRAM/потоков, разрешения управления моделями, размещение моделей, голосовой режим, выбор модели/режима, списки файлов/задач/заметок |

По умолчанию конфиги находятся в `%USERPROFILE%\.neuralsoul\config` (Windows) или `~/.neuralsoul/config`. Путь задаётся JVM-параметром `-Dneuralsoul.configDir=...`. Файлы создаются при первом запуске. Формат UTF-8 Java Properties; запись через временный файл и замену. Изменения через GUI применяются без перезапуска; ручные изменения файлов требуют перезапуска либо вызова `reload()` соответствующего загрузчика.

Старые настройки ресурсов из Java Preferences автоматически импортируются при отсутствии `gui.properties`. `SettingsStore` теперь является адаптером между JavaFX `AppState` и `ConfigLocator.gui()`. Прямого доступа к Preferences в рабочем приложении нет, кроме одноразового чтения старых настроек.

Секрет API не хранится в конфиге: поле **Имя env-переменной API key** принимает имя переменной окружения, из которой клиент читает ключ и формирует `Authorization: Bearer ...`. Для обычного локального сервера оставьте поле пустым.

## Интерфейсы и сервисы

`ServiceLocator` хранит **интерфейсы**, без приведения к конкретным реализациям:

```java
services.llm();       // LlmService
services.stt();       // SttService
services.tts();       // TtsService
services.player();    // AudioPlayer
services.recorder();  // AudioRecorder
```

Общий `ManagedService`: `start()`, `stop()`, `isRunning()`, `close()`.

- `LlmService.generate(List<ConversationTurn>, String model)` и `listModels()`.
- `SttService.convertSpeechToText(byte[] wav)`; алиас `convertSpeekToText` для исходного написания.
- `TtsService.convertTextToSpeech(String text)`; алиас `convertTextToSpeak`.
- `AudioPlayer.play(byte[] wav)`.
- `AudioRecorder.finishRecording()` возвращает WAV.

Методы клиентов синхронные и выполняются на рабочем потоке пайплайна, не на JavaFX Application Thread. `GenerationPipeline` предоставляет асинхронные `generate`, `generateFromSpeech`, `generateFromAudioFile`, `startRecording`, `finishRecording`, `refreshModels`, `connect`, `disconnect`, `testSpeech`.

У HTTP-клиентов `start()` проверяет доступность, а `stop()` отключает клиент. Это **не загрузка/выгрузка модели и не остановка внешнего процесса**. `isRunning()` означает состояние подключения после последней проверки/запроса, а не непрерывный мониторинг сервера. Пустой healthPath означает проверку доступности HTTP-сервера через `/`; ответ 404/405 также подтверждает доступность транспорта, но не готовность конкретной модели.

Чтобы заменить STT/TTS/LLM, реализуйте соответствующий интерфейс и передайте свою реализацию в конструктор `ServiceLocator`. Пайплайн и GUI менять не нужно. `ServiceLocator.local(configs)` — фабрика стандартных HTTP-клиентов и Java Sound аудио.

## Пайплайн

Текст: пользовательский текст → сборка контекста → LLM → показ ответа → необязательный TTS → проигрывание WAV.

Голос: микрофон / WAV → STT → показ распознанного текста → та же цепочка LLM/TTS.

- Выполнение последовательное: одновременно один запрос или управляющая операция.
- Контекст: системный промпт + последние пары сообщений + новый запрос. Лимит **символьный**, не точный токенизатор модели. `max_tokens` — отдельный предел ответа сервера.
- Текст показывается сразу после LLM; синтез и воспроизведение продолжаются после этого.
- Ошибка TTS не уничтожает ответ LLM; отображается сообщение об ошибке озвучивания.
- Отмена прерывает рабочую задачу и HTTP-ожидание, закрывает аудиолинии, отбрасывает поздние UI-события. Сам сервер может закончить уже начатое вычисление согласно собственной реализации отмены.
- Новый чат очищает внутреннюю историю и не принимает поздний ответ старой генерации.
- Режим «Глубокий анализ» меняет инструкцию к ответу. «Автономный» формирует план; самостоятельное выполнение инструментов не реализовано.
- История текущего разговора пока хранится в памяти. Списки файлов/задач/заметок сохраняются при сохранении настроек и закрытии.

## Поддерживаемые HTTP-протоколы

| Сервис | Значения по умолчанию | Контракт |
|---|---|---|
| LLM | `http://127.0.0.1:8080`, `/v1/chat/completions` | JSON messages; ответ `choices[0].message.content`; `stream=false` |
| Список моделей | тот же Base URL, `/v1/models` | `data[].id` |
| STT | `http://127.0.0.1:4213`, `/v1/audio/transcriptions` | multipart `file`, `model`, `language`, `response_format=json`; ответ `{ "text": "..." }` либо простой текст |
| Coqui TTS | `http://127.0.0.1:5002`, `/api/tts` | GET `text`, `speaker_id`, `language_id`; ответ RIFF/WAVE |
| OpenAI-compatible TTS | адрес вашего сервера, `/v1/audio/speech` | POST `input`, `model`, `voice`, `speed`, `response_format=wav`; ответ RIFF/WAVE |

Название модели/движка не определяет API. Ваш portable faster-whisper может иметь другой маршрут: задайте его в форме. Если он принимает не multipart или возвращает другой JSON, нужен адаптер `SttService`. F5-TTS подключается через совместимый HTTP-сервер; прямого запуска Python/ONNX из этого патча нет. Coqui поддержан в варианте API с `speaker_id` / `language_id`; версии сервера с иным контрактом потребуют адаптера. Для XTTS укажите существующий speaker ID на вашем сервере.

Источники контрактов:
- https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md
- https://github.com/coqui-ai/TTS/blob/dev/TTS/server/server.py
- https://github.com/matatonic/openedai-whisper

## Что пока не реализовано

- GPU-распределение, автоматическая загрузка/выгрузка и RAM/VRAM-ограничения сохраняются как план конфигурации. Они не меняют параметры уже запущенных внешних серверов. Для этого нужен отдельный supervisor/launcher под конкретные runtimes.
- Автоопределение GPU и их живые метрики. CPU/RAM на главной берутся из JVM/OS при открытии страницы; устройства и размещения в настройках пока являются конфигурацией.
- Исполнение агентских задач, веб-поиск, захват экрана и управление компьютером. Их страницы остаются точками расширения.
- Прикреплённые файлы и заметки автоматически не передаются LLM; в текущий контекст включается история разговора.
- Выбор конкретного микрофона/выхода в GUI: используется устройство Java Sound по умолчанию, запись 16 kHz / mono / PCM16. Воспроизведение — WAV, поддерживаемый Java Sound.

## Проверки

`mvn test` — 9 тестов: реальные HTTP-адаптеры с локальным тестовым сервером, текст и история, STT→LLM→TTS, Coqui, выключенный TTS, ошибка TTS, отмена и очистка контекста, lifecycle, конфиги, JSON, GUI и размеры окон. HTTP-тесты используют подменённые аудиоустройства; реальные GPU, микрофон/динамики Windows и ваши серверы в этой среде недоступны.

`DemoBackend` оставлен для совместимости, но в `NeuralSoulApp` используется `PipelineBackend`. Для тестирования заменяйте сервисы через интерфейсы, а не через приведения типов.
